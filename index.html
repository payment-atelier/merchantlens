Improvement — M-011 Kestrel Provisions
Before
The drafted documentation request named only part of the record’s three gaps: 1 of 3 on the first sweep (the bank-entity mismatch alone) and 2 of 3 on the second (bank entity and projected volume). The pending tax ID was missed both times. Both runs scored 6/6 on exact match — the auto-scorer checks the disposition, not the letter, so nothing flagged it. A human reading the request caught it.
Change
One rule added to Field 10’s contract in the system prompt: the drafted request must name every gap and contradiction in the record, having first walked the whole record — application fields, risk signals, storefront and pages, free-text notes — with an explicit statement that a gap spanning two fields or two files counts the same as one sitting in a single document. The rule names no merchant and no specific gap: writing M-011’s three gaps into the prompt would have fixed one case and taught the agent nothing.
After
3 of 3 gaps named, on both post-fix runs. The request now does the arithmetic itself — $185,000 projected against a 10-item catalog implies roughly 14,000 transactions a month — and asks for the records that would support it. Citations rose 16/16 to 17/17. Disposition, escalation trigger and every structured verdict unchanged, so the fix added evidence without moving a decision. Analyst verdict Needs work to Pass; scoreboard 16/4/0 to 17/3/0.
Known limitations
One chain of three
Only consistency verification reasons live — sufficiency, classification, claim comparison, policy screen. Exposure-based terms sizing (field 7) and reputational adjudication (field 8) are v2 samples supplied by the application; the agent is instructed not to produce them and the parser discards them if it does. A reviewer should never have to guess which fields are reasoning.
Not deterministic
Dispositions are mostly stable, not guaranteed. The same build scored 20/20, then 18/20, then 20/20 on re-run; temperature is left at the API default. Free text moves more than the verdicts do — the drafted request and the policy listing vary run to run while the disposition usually holds. Every case goes to a human, which is what makes this a limitation rather than a defect.
One annotator
Every expected outcome was written by one person before the agent ran. Exact-match scoring measures whether the agent agrees with those labels, not whether the labels are right — a wrong label reads as a wrong agent, and there is no second annotator to catch it. It also cannot see quality inside free text: two cases here score a perfect 6/6 and are still marked Needs work, because reading the drafted output caught what the score could not.
Inputs
Needs data in exactly this shape: one application row per merchant, one JSON storefront per merchant, the fixed policy files, and a 15-code category reference it may not deviate from. English only, one case at a time, no live web retrieval — every storefront and media record here is synthetic. It cannot review a merchant whose evidence lives anywhere else.
No memory
Nothing carries between cases, by design: every merchant is judged on their own file against the same standard, which is the answer to reviewer drift. The cost is that it cannot see across applications — the same principal applying twice under two names reads as two unrelated files.
